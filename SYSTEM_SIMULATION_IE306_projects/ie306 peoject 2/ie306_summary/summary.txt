### 1. Why Simulation? Real-World Motivation
Complex systems with **feedback, interactions, and randomness** produce non-obvious behavior:

- **Black Friday surge**: 5× traffic in 10 minutes → latency explosion (not intuitive).
- **Bank queue**: 3 tellers + sudden arrival surge → long waits. *Trade-off?* Add a 4th teller?
- **Supply chain**: Random demand + random lead time → stockouts *or* excess inventory.

**Humans are poor at reasoning** about feedback loops, emergent patterns, and stochastic processes analytically.

### 2. Core Definitions
**System** (course definition)  
A set of **entities** (components) that **interact over time**, forming an organized whole whose behavior we study.

**Simulation** (course definition)  
The **imitation** of a real system’s operation over time, using a **model** so we can run experiments safely and repeatedly.

**Textbook view** (Banks, Carson, Nelson & Nicol)  
“The imitation of the operation of a real-world process or system over time.”

### 3. Simulation: A Third Way of Doing Science
| Approach              | Strengths                          | Weaknesses                              | Typical Use                  |
|-----------------------|------------------------------------|-----------------------------------------|------------------------------|
| **Real Experiments**  | Direct reality                     | Costly, risky, sometimes impossible    | Physics, chemistry, biology |
| **Mathematical Analysis** | Elegant, exact (when solvable) | Limited by tractability                | LP, queueing theory         |
| **Simulation**        | Safe, cheap, repeatable, flexible | Requires skill; results are estimates  | **This course**             |

**Simulation borrows** modeling + experimentation without physical risk or math limits.

### 4. Ways to Study a System
**System**  
├── Experiment with Actual System (costly, risky, disruptive)  
└── Experiment with a **Model**  
  ├── Physical Model (wind tunnel)  
  └── Mathematical Model  
    ├── Analytical Solution (queuing formulas)  
    └── **Simulation** ← **This course**

### 5. What Simulation IS — and Is NOT
**Simulation IS**  
- Computational experimentation  
- Tool for “what if” questions  
- Model-driven decision support  
- Reproducible & transparent  
- Under-the-hood engineering

**Simulation is NOT**  
- Animation (pretty pictures ≠ science)  
- Optimization (evaluates, doesn’t auto-find optimum)  
- Prediction/prophecy  
- Pure probability proofs  
- Substitute for thinking

**Workflow**  
Ask a Question → Build a Model → Run Experiments → Make a Decision

### 6. Why We Simulate (When Math Fails)
- Feedback loops create non-obvious behavior  
- Interacting agents produce **emergent patterns** (e.g., mild preferences → segregation)  
- Stochastic processes make averages misleading  
- Real experiments are too expensive/risky/impossible  
- Analytical math breaks on real complexity

**Emergent segregation example** (Schelling 1971):  
Agents want ≥ threshold % same-type neighbors → simple local rule creates global segregation. *No one planned it. You cannot predict analytically — you must simulate.*

### 7. When to Simulate — and When NOT
**Use Simulation When…**  
- System too complex for analytical solution  
- Need to study internal behavior over time  
- Real experiments too expensive/risky  
- Need to compare designs before building

**Don’t Simulate When…**  
- Problem solvable analytically  
- Input data unavailable and cannot be estimated  
- Expectations unrealistic (“find the optimum”)  
- Simpler methods suffice

### 8. Advantages vs. Disadvantages
**Advantages**  
- Test without disrupting real system  
- Explore “what if” safely  
- Compress/expand time  
- Study extreme conditions  
- Models are reusable

**Disadvantages**  
- Model building requires skill & time  
- Stochastic output needs statistical analysis  
- False confidence if unvalidated  
- Results are estimates, not exact  
- Garbage in, garbage out

**Lecture 02 Summary: General Principles of DES**  
**Basic definitions, concepts, and hand simulation**  
Kerem Demirtas — Boğaziçi University, IE 306, Spring 2026

### 1. Core DES Concepts (Review + New)
- **Entities**: Objects that move through the system (e.g., customers, parts, calls).
- **Attributes**: Properties attached to each entity (e.g., arrival time, type, service need).
- **Events**: Instantaneous occurrences that change the system state (arrival, departure).
- **Event Notice**: “Event X at time t”.
- **Future Event List (FEL)**: Sorted list of all scheduled event notices (by time).
- **Clock**: Current simulated time — advances **only** to the next event time (next-event time advance).
- **State Variables**: Describe the system at any moment (e.g., server busy/idle, queue length). Change **only** at events.
- **Activity**: Known-duration interval whose end is scheduled as an event in the FEL (e.g., service time = 4 min → schedule departure at t+4).
- **Delay**: Unknown-duration wait that ends when a condition becomes true (e.g., wait in queue until server free) — **not** put in FEL.

### 2. How Time Advances in DES (Next-Event Time Advance)
1. Remove the **imminent** (earliest) event from the FEL.  
2. Advance clock to that event’s time.  
3. Execute the event → update state variables, statistics, lists.  
4. Schedule any new events and insert them into the FEL (sorted by time).  
5. Update statistical accumulators.  

Repeat until FEL is empty or a stopping condition is met.  
**Simulated time jumps** from event to event — far more efficient than ticking every unit of time.

### 3. Single-Server Queue — Hand Simulation (Main Example)
**System**  
- One machine (server), FIFO queue, infinite buffer.  
- Initially empty and idle at t = 0.  
- Stop at t = 20 minutes.  
- Given interarrival and service times for the first 11 parts.

**State variables tracked**:
- Clock  
- Server status B(t) (0 = idle, 1 = busy)  
- Queue length Lq(t)  
- List of arrival times of customers currently in queue  

**Event logic**:
- **Arrival**:  
  - Update time-persistent stats (area under Lq(t) and B(t) curves).  
  - Mark arriving part with current time.  
  - If server idle → start service, schedule departure, waiting time = 0.  
  - Else → join queue, increase Lq.  
  - Schedule next arrival.  
- **Departure**:  
  - Increment production counter.  
  - Tally time-in-system for the departing part.  
  - Update time-persistent stats.  
  - If queue non-empty → remove first part, tally its queue wait, start service (schedule new departure).  
  - Else → server becomes idle (no new departure scheduled).  
- **End (stopping event)**: Update final time-persistent stats and compute all output measures.

**Performance measures calculated from hand simulation (t = 20)**:
- Avg. waiting time in queue = 2.53 min/part  
- Time-average number in queue = 0.79  
- Server utilization = 0.92  

### 4. Randomness in Simulation
One run = **one replication** (sample of size 1).  
Run **multiple independent replications** (different random seeds) → compute sample mean, std. dev., and confidence intervals:

\[
\bar{X} \pm t_{n-1,1-\alpha/2} \frac{s}{\sqrt{n}}
\]

Example table (5 replications) shows substantial variability across runs; CIs are therefore essential.

### 6. DES Engine & Two World Views
**DES Engine** (flowchart): Initialize → while FEL not empty → get next event → advance clock → process event → schedule new events → repeat → report statistics.

**Two World Views**:
- **Event Scheduling** (what we did by hand): Focus on “what happens next?” Maintain sorted FEL. Good for procedural coding.
- **Process Interaction** (used by SimPy): Focus on “what does one entity experience?” (arrive → request server → wait → get served → leave). Reads like a story; engine hides the FEL details.

**Both produce identical results**; underneath, everything is still event scheduling.

### 7. From Hand Simulation to Code
Everything done on paper maps directly to code:
- FEL → priority queue (heapq)
- Clock → `env.now` in SimPy
- Event processing → Python functions/generators
- State → variables/objects/lists
- Statistics → accumulators

### 2. What Is SimPy?
- **Process-based Discrete-Event Simulation** library for Python (free & open-source).  
- Docs: simpy.readthedocs.io  
- Uses **process interaction** worldview (from Lecture 2).  
- Built-in FEL & clock management.  
- Uses Python **generators** (`yield`) to model entity lifecycles.  

**Basic setup**:
```python
import simpy
env = simpy.Environment()
env.run(until=100)   # or until FEL is empty
```

### 3. The Three Core Objects in SimPy
| Object     | Purpose                              | Key Features                     |
|------------|--------------------------------------|----------------------------------|
| **env**    | Simulation world                     | Holds clock (`env.now`), FEL, runs simulation |
| **Process**| Entity’s lifecycle (generator)       | Uses `yield` for delays/activities |
| **Resource**| Contested object (teller, machine)  | Limited capacity, `request()` / `release()` |

### 4. Environment (`env`)
- `env.now`: current simulation time (read-only)  
- `env.process(...)`: register a process  
- `env.run(until=T)`: run until time `T` (or until FEL empty)  
- `env.timeout(t)`: delay for `t` time units  

SimPy automatically handles the **next-event time advance** you did manually in Lecture 2.

### 5. Python Generators Refresher
Regular functions run to completion.  
**Generators** (`yield`) can **pause and resume** — exactly what we need for:
- Waiting in queue  
- Service activity  
- Arrivals, etc.

### 6. Processes & Resources
**Process** = one entity’s story:
```python
def customer(env, name, teller, arrival, service):
    yield env.timeout(arrival)          # arrive
    with teller.request() as req:       # request server
        yield req                       # wait until granted
        yield env.timeout(service)      # service (activity)
```

**Resource** = server/teller:
```python
teller = simpy.Resource(env, capacity=1)
```
`with ... as req:` automatically releases the resource when the block ends.

### 8. Full Working Code (Bank Anchor v3)
```python
import simpy
wait_times = []

def customer(env, name, teller, arrival, service):
    yield env.timeout(arrival)
    arrive_time = env.now
    with teller.request() as req:
        yield req
        wait = env.now - arrive_time
        wait_times.append(wait)
        print(f'{name}: arrive={arrive_time:.0f}, start={env.now:.0f}, wait={wait:.0f}')
    yield env.timeout(service)

env = simpy.Environment()
teller = simpy.Resource(env, capacity=1)

env.process(customer(env, 'C1', teller, 0, 4))
env.process(customer(env, 'C2', teller, 2, 3))
env.process(customer(env, 'C3', teller, 8, 3))
env.process(customer(env, 'C4', teller, 10, 2))

env.run()
print(f'\nAvg wait: {sum(wait_times)/len(wait_times):.2f}')
```

### 5. Traffic Intensity, Stability & Little’s Law
**Traffic intensity**:
- Single server: \(\rho = \lambda / \mu\)
- \(N\) servers: \(\rho = \lambda / (N\mu)\)

**Stability**: \(\rho < 1\) required, otherwise queue → ∞.

**Little’s Law** (any stable queue): \(L = \lambda W\)  
(where \(L\) = avg # in system, \(W\) = avg time in system).

**M/M/1 waiting time** (derived step-by-step):
\[
W_q = \frac{\rho}{\mu(1-\rho)}
\]

**Bank example** (\(\lambda = 1/3\), \(\mu = 1/4\)):
- \(N=1\): \(\rho \approx 1.33\) → unstable
- \(N=2\): \(\rho \approx 0.67\) → stable, avg wait ≈ 4.8 min
- \(N=3\): \(\rho \approx 0.44\) → stable, avg wait ≈ 0.4 min

### 6. Separate Resources vs. Pooled Capacity
- **Interchangeable servers** → `Resource(capacity=N)`
- **Different speeds / preferences** → separate resources + routing

### 7. OOP Refactoring — `Customer` Class
Motivation: procedural `customer()` becomes unwieldy with many customer types.

```python
class Customer:
    def __init__(self, env, name, teller, arrival, service):
        self.env = env
        self.name = name
        ...
        self.process = env.process(self.run())   # auto-starts

    def run(self):
        yield self.env.timeout(self.arrival)
        arrive_time = self.env.now
        with self.teller.request() as req:
            yield req
            self.wait = self.env.now - arrive_time
            yield self.env.timeout(self.service)
```

**Subclass example** — `ImpatientCustomer` (balks if queue too long):

```python
            print(f'{self.name} balks')
            return
        ...
```

|-------------|------|------------|

### 3. SimPy Internals (How It Really Works)
- **FEL**: `heapq` of `(time, event_id, event)` triples (time-ties broken by insertion order)
- **env.step()**: Pop smallest event → advance `env.now` → call all callbacks → wake processes
- **env.run(until=T)**: Loop of `step()` until time T
- **Event hierarchy**: `Timeout` → `Process` → `Condition` (`AnyOf` = OR, `AllOf` = AND)
- **Callbacks**: Every event has `.callbacks` list; `yield` appends resume function; `env.step()` executes them

**Key debugging tool**:
```python
print(env.peek())   # next event time (or inf if empty) — read-only
```

### 4. OR Condition (`AnyOf`) — Reneging
```python
req = server.request()
result = yield req | env.timeout(patience)
if req in result:          # served
    ... service ...
else:                      # reneged
    req.cancel()           # MANDATORY!
    reneges += 1
```

**Rule**: Always call `req.cancel()` on renege, otherwise a ghost request stays in the queue forever.

### 5. AND Condition (`AllOf`) — Synchronization
```python
room_req = rooms.request()
doc_req  = doctors.request()
yield room_req & doc_req     # wait for BOTH
# now hold both resources
yield env.timeout(treatment)
doctors.release(doc_req)
env.process(clean_room(..., room_req))  # delayed release
```

**Deadlock prevention**: Submit **all** requests first, then yield the `&` condition.

### 6. Priority & Preemption
| Feature              | Class                  | Behavior                              |
|----------------------|------------------------|---------------------------------------|
| Non-preemptive       | `PriorityResource`     | Queue sorted by priority; no interrupt |
| Preemptive           | `PreemptiveResource`   | Higher priority interrupts current job |

**Preemption code pattern** (must catch `simpy.Interrupt`):
```python
remaining = service_time
while remaining > 0:
    req = machine.request(priority=p, preempt=True)
    try:
        yield req
        yield env.timeout(remaining)
        remaining = 0
    except simpy.Interrupt:
        remaining -= (env.now - start)
    finally:
        machine.release(req)
```

**From the Engine to the Data**

**What you didn’t know** → How the PRNG actually works, why streams must stay independent, and how to turn real service-time data into the correct distribution for your SimPy model.

### 2. Part A — The PRNG Engine

#### Linear Congruential Generator (LCG) — The Simplest Engine
\[
x_{n+1} = (a \cdot x_n + c) \mod m, \quad u_n = \frac{x_n}{m} \in [0,1)
\]
- Seed \(x_0\) sets the starting point.
- Same seed → **exact same sequence** every time (reproducibility).

**Period**: Maximum \(m\) (with careful \(a,c,m\)).  
numpy’s **PCG64** has period \(2^{128} \approx 3.4 \times 10^{38}\) — more than enough for any simulation.

#### What “Random” Means Here — Tests
| Test                  | What it checks                              | Good result (PCG64) |
|-----------------------|---------------------------------------------|---------------------|
| Histogram             | Uniform fill of [0,1]                       | ✓                   |
| Scatter plot \((u_n, u_{n+1})\) | No correlation between consecutive draws | ✓ (no visible lines) |
| Autocorrelation       | \(\hat{\rho}_k \approx 0\) for \(k \ge 1\) | All lags inside ±1.96/√n band |
| Chi-square            | Bin counts match expected                   | Large \(p\) (>0.05) |
| KS test               | Full CDF shape matches \(U(0,1)\)           | Large \(p\)         |
| t-test                | Mean ≈ 0.5                                  | Large \(p\)         |

**Takeaway**: Never implement your own LCG. Trust `np.random.default_rng()`.

### 3. Random Variate Generation — Inverse Transform
**Continuous** (e.g. Exponential):
\[
F(x) = 1 - e^{-x/\mu} \quad \Rightarrow \quad X = -\mu \ln(U)
\]
`rng.exponential(mean)` does exactly this.

**Discrete** (Lecture 1 style):
Use cumulative probabilities → `rng.choice(values, p=probs)`.

**When CDF has no closed inverse** (Normal, Gamma…):  
numpy uses ziggurat / acceptance-rejection internally.

### 4. RNG Best Practices in SimPy Models (Critical!)

**The Three Rules**
1. **Always** use `default_rng(seed)` — never legacy `np.random.*` or `random.seed()`.
2. **One RNG per source** (interarrivals, service times, routing, logging…).
3. **Document your seeds** (commit `BASE_SEED` with the code).

**Contamination problem**  
One extra `rng.random()` (e.g. for logging) shifts **all** downstream variates → completely different experiment.  
**Fix**: Give every random source its own `rng` object.

**Seed management for replications & debugging**
- Development: fixed seed + `VERBOSE=True`.
- Production: `BASE_SEED` + `SeedSequence` for independent streams.
- CRN (Common Random Numbers) preview: same seeds across scenarios for fair comparison.

**Why Pandas?**

```python
df = pd.read_csv('service_times.csv')
df.describe()                    # mean, std, quartiles, CV
df.groupby('teller')['service_time'].describe()

```

### 6. Part C — Input Analysis (Choosing the Right Distribution)

**Key diagnostic: Coefficient of Variation (CV = std/mean)**
- CV ≈ 1.0 → Exponential (memoryless)
- CV < 1.0 → Lognormal / Gamma / Erlang (mode > 0)
- CV > 1.0 → heavier tails (Weibull)

**Visual tools**
- **Histogram** + overlaid PDF (density=True)
- **Q-Q plot** (straight diagonal = excellent fit)

**Q-Q Plot Patterns**
| Pattern              | Meaning                              | Action                              |
|----------------------|--------------------------------------|-------------------------------------|
| Points on diagonal   | Good fit                             | Accept                              |
| S-curve              | Lighter tails than assumed           | Try lighter-tailed family           |
| Reverse-S            | Heavier tails                        | Try heavier-tailed family           |
| Right end below      | Shorter right tail (over-dispersed)  | Switch from Exponential             |

**Common families**
- Exponential: interarrivals, pure random waiting
- Lognormal: service times (product of many small factors)
- Gamma/Erlang: multi-phase service
- Weibull: reliability / failures (hazard can increase/decrease)

**Fitting workflow**
```python
import scipy.stats as stats
# Exponential
loc, scale = stats.expon.fit(data, floc=0)   # force min=0

# Lognormal
shape, loc, scale = stats.lognorm.fit(data, floc=0)
mu_ln = np.log(scale)
sigma_ln = shape

# Automated comparison
from fitter import Fitter
f = Fitter(data, distributions=['expon','lognorm','gamma','weibull_min'])
f.fit()
f.summary()          # SSE, AIC, BIC ranking
```

**Final model update**  
Bank data: right-skewed, CV ≈ 0.59, mode > 0 → **Lognormal** (not Exponential).  
Result: average wait drops ~40% compared to old Exponential model.

### 2. Section 2 — Engineering Practices (Avoid Spaghetti)

**Spaghetti anti-pattern** (one giant `customer()` function):
- All routing, service, stats, and rework logic interleaved
- Untestable, unmaintainable, impossible to add stages

**Clean entity lifecycle pattern**:
```python
def coat(env, machine, rng, priority=2):
    with machine.request(priority=priority) as req:
        yield req
        yield env.timeout(rng.gamma(2, 2))
    # auto-release

def inspect(env, qc, rng):
    with qc.request() as req:
        yield req
        yield env.timeout(rng.exponential(1.0))
    return rng.random() > 0.20  # pass/fail

def batch(env, resources, rng, stats, k):
    arrival = env.now
    rework_count = 0
    while True:
        pri = 1 if rework_count > 0 else 2
        yield from coat(env, resources['coating'], rng, pri)
        passed = yield from inspect(...)
        if not passed:
            rework_count += 1
            if rework_count > k:
                stats['scrapped'] += 1
                return
        else:
            yield from package(...)
            stats['flow_time'].append(env.now - arrival)
            return
```

**Key mechanisms**:
- **`yield from sub()`**: Sequential delegation (clean, testable, returns value)
- **`timeout(0)`**:
  - Correct use: enforce deliberate ordering at simultaneous times (e.g., inventory replenishment before demand)
  - Rule: Never use to “fix” a symptom — investigate root cause
  - Danger: Hides insertion-order bugs
- **Instrumentation**: Record **at the exact event** (`arrival` before first `yield`; wait at service start)
- **OOP entity pattern** (`run()` method): Use when entities carry state across stages or have type-specific parameters (Standard vs. Premium)

**Practices checklist** (use this before every model):
- One function per actor
- Record stats at event time
- `yield from` for sequential steps
- `timeout(0)` only with explicit justification
- OOP only when functional hurts

### 3. Section 3 — Bank Network (Series Queues)

**Series (tandem) queues**:
- Customer finishes Stage 1 → immediately requests Stage 2
- **Cycle time (CT)**: time between consecutive outputs
- **Flow time (sojourn)**: total time a customer spends in system

**Bottleneck rule**:
\[
\text{TH}_{\text{sys}} = \min_i \frac{1}{E[S_i]} = \frac{1}{\max_i E[S_i]}
\]
Highest utilization + longest queue = bottleneck.

**Cascade effect**:
- Variability from upstream propagates downstream
- Downstream queues more variable than upstream (even at same ρ)

**SimPy chaining pattern** (clean series):
```python
with stage1.request() as req:
    yield req
    yield env.timeout(rng.exponential(2.0))
with stage2.request() as req:   # Stage 1 auto-released
    yield req
    yield env.timeout(rng.exponential(4.0))
```

**Probabilistic split**:
```python
if rng.random() < 0.40:
    # go to teller
```

**Merging flows**:
- Two independent `arrivals_*()` generators calling the same Resource
- SimPy merges contention automatically

**Per-stage statistics** reveal the true bottleneck (longer waits + higher queue at Teller, not ATM).

### 4. Section 4 — Pharmaceutical Tablet Model (Feedback + Priority)

**System**:
- New batches arrive Poisson(λ = 1/5)
- Coating (Gamma) → QC (Exp) → Packaging (Exp)
- 20% fail QC → re-coat (higher priority) or scrap after k failures

**Hidden load**:
- Effective arrival rate at coating: \(\lambda_{\text{eff}} = \lambda / (1 - p_{\text{fail}})\)
- At \(p_{\text{fail}} = 0.20\): \(\lambda_{\text{eff}} \approx 0.25\) → utilization jumps to 1.00

**k as load-control lever**:
- Caps re-entries → bounds hidden load
- Scrap probability ≈ \(p^{k+1}\)
- \(k=3\) captures ~98% of unlimited-rework load

**PriorityResource**:
```python
coating = simpy.PriorityResource(env, capacity=1)
req = coating.request(priority=PRIORITY_REWORK)  # lower number = higher priority
```
Non-preemptive by default.

**OOP for heterogeneous batches**:
```python
class TabletBatch: ...          # COATING_MEAN=4.0, P_FAIL=0.15
class PremiumBatch(TabletBatch): # overrides only parameters
```
`run()` inherited unchanged.

**Policy comparison** (4 policies):
- A: 1 machine, FCFS
- B: 1 machine, Priority (rework first)
- C: 2 machines, FCFS
- D: 2 machines, Priority

**Key insights**:
- Priority redistributes waiting time (rework benefits, new batches pay the price)
- Starvation appears when \(p_{\text{fail}}\) high
- Pareto frontier: \(k=3\) nearly optimal (minimal extra scrap, big flow-time reduction)
- 2 machines eliminate priority benefit (queues rarely build)

### 1. Agenda & Big Picture

**Core shift from L3–L7**:  
`request()`/`release()` = **borrow a slot, use it, return it** (capacity constant).  
`put()`/`get()` = **produce & consume items** (contents change over time).

### 2. Resource Taxonomy (Decision Tree)
Start here when designing any new component:

| Question                        | Yes → Resource Type          | Typical Use                     |
|--------------------------------|------------------------------|---------------------------------|
| Entity borrows & returns?      | Resource family (L3–7)      | Machines, servers, pumps       |
| Bulk/fungible quantity?        | **Container**                | Fuel, supplies, raw material   |
| Distinct objects?              | —                            | —                              |
| → Need attribute selection?    | **FilterStore**              | Inventory, tool crib           |
| → Items have priority?         | **PriorityStore**            | Orders, ER triage, express     |
| → Simple FIFO?                 | **Store**                    | Message queue, conveyor buffer |

**Comparison Table** (key differences):

| Feature          | Resource          | Store          | FilterStore       | PriorityStore     | Container          |
|------------------|-------------------|----------------|-------------------|-------------------|--------------------|
| Models           | Slots             | Object queue   | Object queue      | Object queue      | Bulk quantity      |
| API              | request/release   | put/get        | put/get(filter)   | put/get           | put(n)/get(n)      |
| Blocks put       | All busy          | Full           | Full              | Full              | Level > cap        |
| Blocks get       | No                | Empty          | No match          | Empty             | Level < amount     |
| Retrieval        | —                 | FIFO           | Predicate         | Priority          | Fungible (no ID)   |
| Default capacity | 1                 | ∞              | ∞                 | ∞                 | User-specified     |
| Item identity    | No                | Yes            | Yes               | Yes               | No                 |

**Critical note**: Store family default capacity = ∞ (items never block on `put()` unless you set a finite value).

### 3. Store Family Details
- **Store** (FIFO object queue): `yield store.put(item)`, `item = yield store.get()`. `store.items` is a plain Python list of your objects.
- **FilterStore** (selective retrieval): `item = yield fstore.get(filter=lambda i: i.category == "food" and i.weight < 2)`. Non-FIFO by design (later request can overtake if filter matches).
- **PriorityStore**: Uses `simpy.PriorityItem(priority, item)`. Lower number = higher priority.

**Common patterns**:
- Producer–consumer (backpressure when buffer fills)
- Batch processing: `items = [yield store.get() for _ in range(N)]`

### 4. Container (Bulk Flow)
- Holds a level (int/float), fungible items.
- `yield tank.put(30)` / `yield tank.get(25)`
- Blocks on full (put) or insufficient level (get).
- Atomic: all-or-nothing (no partial fills).
- Classic example: Gas station tank (periodic tanker refill at threshold).

**Container vs Store**:
- Store → “give me that specific item”
- Container → “give me 25 units”

### 5. Act 2: Disruptions & Coordination
**Manual events** (`env.event()`):
- Bare event for signaling/broadcasting.
- `signal = env.event()`; `signal.succeed(value)` wakes all waiters.
- Pattern: `result = yield shift_end | env.timeout(work)`

**process.interrupt()** (external disruption):
- Throws `simpy.Interrupt` into a yielding process.
- Catch with `try/except simpy.Interrupt as ir:`.
- Record elapsed time → repair → resume remaining service.
- **Guard before interrupting** (preferred design): check machine state first to avoid nested interrupts.

**Breakdown pattern** (machine + breakdown process):
- Machine: try/except around `timeout(svc_time)`
- Breakdown: `yield timeout(mttf)` → `proc.interrupt("failure")`
- Optional: spare parts from a Store (repair waits for both part + repair time).

### 6. Capstone: Fulfillment Center (All Patterns Combined)
**System**:
- **PriorityStore**: Order queue (express before standard)
- **FilterStore**: Shelves (SKU/category/weight filtering)
- **Store**: Conveyor buffers (picker_out → packer_in)
- **Container**: Packing supplies (fungible units)
- **interrupt()**: Conveyor breakdown/repair
- Periodic restock (every 60 min)

**Key modeling choices**:
- Separate RNG streams per source (6 streams)
- `placed_at` timestamp for end-to-end latency
- Conveyor breakdown process runs independently
- Packer consumes 1 supply unit per order

**Three experiments** (results in full lecture):
- Experiment 1: Baseline (no breakdowns, infinite supplies)
- Experiment 2: Add conveyor breakdowns
- Experiment 3: Vary picker/packer counts + supply policy

**Design insights**:
- Starvation risk in PriorityStore (express orders starve standard)
- Non-FIFO in FilterStore (rare SKU orders can wait forever)
- Container level plot = visual health of the system (sawtooth)
- Bottleneck signals: empty packer_in (conveyor), empty supplies (supply chain)
